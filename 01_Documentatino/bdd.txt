BASE DE DONNÉES « makegiver » 

utilisateurs : UtilisateurID (PK), Nom, Prenom, Email (unique), Telephone, MotDePasse_Hash, Role (enum : Membre, Maker, Soignant, Admin), Bio_Description, Competences_Techniques, Consentement_Public (booléen — visibilité du profil / RGPD), Date_Inscription, pseudo, Region.

projets (Besoins) : ProjetID (PK), Titre_Besoin, Description_Detaillee, Statut (enum : Ouvert, En cours, Terminé), Date_Creation, Date_MiseAJour, DemandeurID (FK → utilisateurs), maker_id (FK → utilisateurs : le maker retenu pour le besoin).

solutions : SolutionID (PK), Titre_Solution, Description_Technique, Licence, Materiel_Necessaire, Difficulte_Fabrication, Date_Publication, Est_CoupDeCoeur (booléen), CreateurID (FK → utilisateurs), CoAuteurID (FK → utilisateurs).

candidatures : id (PK), projet_id (FK → projets, ON DELETE CASCADE), maker_id (FK → utilisateurs, ON DELETE CASCADE), date_candidature. — Un maker se propose pour répondre à un besoin ; le demandeur valide ensuite l'un des volontaires (qui devient projets.maker_id).

fichiers : FichierID (PK), Nom_Fichier, Chemin_URL, Type, Taille_Mo, SolutionID (FK → solutions, optionnel), ProjetID (FK → projets, optionnel). — Fichiers joints (STL, PDF, images) téléversés sur une solution.

commentaires : CommentaireID (PK), Contenu_Texte, Date_Post, Est_Valide (booléen — modération : 1 affiché, 0 masqué), AuteurID (FK → utilisateurs), SolutionID (FK → solutions, optionnel), ProjetID (FK → projets, optionnel). (Pas de système de notation par étoiles.)

signalements : SignalementID (PK), UtilisateurID (FK → utilisateurs, l'auteur du signalement), TypeContenu (Solution, Besoin, Commentaire, Evenement, Profil), ContenuID (identifiant du contenu visé), Raison, Date_Signalement.

evenements (Agenda externe) : EvenementID (PK), Titre_Event, Description, Date_Debut, Date_Fin, Type, Lien_Externe_Organisateur. — Événements organisés en dehors du site (renvoi vers le lien de l'organisateur).

lieux (Annuaire) : LieuID (PK), Nom_Lieu, Adresse_Complete, Code_Postal, Ville, Coordonnees_GPS, Type, Liste_Equipements. — Table disponible pour des lieux saisis manuellement ; en pratique, l'annuaire des FabLabs affiché sur le site est alimenté en direct par l'API externe fablabs.io.

categories : CategorieID (PK), Nom_Categorie, Type_Categorie, Description. — Table présente, pas encore reliée aux besoins/solutions dans l'application.

membresprojet (table de liaison) : ProjetID (FK → projets), UtilisateurID (FK → utilisateurs), RoleSurProjet. — Présente dans le schéma, non utilisée par l'application actuelle.


ÉCARTS AVEC LA CONCEPTION INITIALE (pour mémoire)
- Ajout de la table « candidatures » (un maker postule, le demandeur valide le collaborateur).
- Authentification : connexion classique sécurisée (mot de passe haché en bcrypt, protection CSRF). La double authentification (F2A) envisagée au départ n'a pas été implémentée.
- Le consentement RGPD est géré par le champ booléen « Consentement_Public » de la table utilisateurs (pas de table « Consentements » dédiée).
- Tables envisagées mais non implémentées : ProjetsCategories, SolutionsCategories, Consentements.
- L'e-mail et le téléphone ne sont jamais exposés publiquement : un profil public n'affiche que pseudo, rôle, et — si l'utilisateur y a consenti — nom, région, bio et compétences.
